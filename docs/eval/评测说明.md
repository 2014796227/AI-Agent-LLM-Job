# 评测体系说明

## 1. 评测集构成与来源

- 用例存放：`evals/cases/*.yaml`（多文档流式分隔）；全集目标 45~65 条（M5 由你审核定稿——AI 生成候选 + 你删改定稿，符合 provenance 的"AI 初稿+人工审核"）
- 三类用例：投研报告 15~20 ｜ 回测 10~15（**绝对日期窗口**+冻结快照 fixture）｜ RAG 问答 20~30（从语料反向生成并标注原文出处）
- 特殊用例：**正确拒绝**（白名单外需求，refusal_ok=通过才对）；边界用例（含涨停日策略，验证假设脚注展示）
- 快照：`evals/fixtures/*.parquet`，meta 必含 fetched_at/checksum/akshare_version——跨版本对比一律对快照复算（消除数据源漂移，ADR-0003）；快照必须为 `fetch_combined` **完整 10 列帧**（date 索引 + OHLCV × hfq/raw，文件名中 hfq 指计算口径非列范围；`tools._load_fixture` 加载即校验，v18 P2-1）

## 2. 三层评测方法（按可客观程度递降）

1. **确定性断言**（全自动）：工具调用轨迹（task_events）、DSL spec 结构比对、回测三元组本地复算（tolerance 1e-9）、引用文本∈所引页、numbers_ok（指标格式变体出现在报告中）
2. **LLM-as-judge**（免费 Flash 当裁判，辅助不替代）：报告完整性/论据支撑/幻觉倾向，输出 {"pass", "issues"}
3. **人工抽查**（你执行，每轮 20%）：按 acceptance checklist 打分，结论追加于报告末尾（唯一允许的人工编辑位置）

## 3. 报告生成制（provenance 契约）

`python scripts/run_eval.py --cases evals/cases --out docs/eval/results.md --timeout-min 10`

- results.md 100% 由脚本生成：自动嵌 commit hash、时间戳、每用例七列（状态/tools/spec/backtest/numbers/refusal/judge）
- 人工只在末尾追加"结论与归因"段；改数据=违反 provenance
- 版本对比：不同 commit 各跑一次全量，汇总表由脚本输出（不手填）

## 4. 真实失败沉淀

每周实测中的失败案例（尤其 AKShare 失效、模型幻觉数字、工具死循环熔断）转化为回归用例——评测集最重要的来源是真实失败，不是纸面设计。
