# 产出物真实性与可追溯性规范（provenance）

> 本文件是所有项目产出物的**元规范**。原则：**一切产出物源于真实事件，可追溯、可复现、有数据支撑；没有发生的事不写。**
> 本规范本身自 v5 蓝图引入，历经六轮评审未变——它是本项目区别于"编故事型求职项目"的底线。

## 一、逐类产出物的真实来源与禁止事项

| 产出物 | 真实来源（追溯链） | 禁止事项 |
|---|---|---|
| 事故复盘（docs/postmortem/） | 只写真实发生的事：必附 GitHub Issue 编号、trace_id + 结构化日志原文片段、当时 commit hash、时间线 | **不设数量指标，无事故则无此文档**；不为凑数把预演当事故 |
| 故障预判与验证清单（docs/verification/） | PoC/M0 阶段每个预判故障点的真实触发与修复记录（命令与输出原文）——与"事故复盘"分开命名 | 不冒充生产事故 |
| 评测报告（docs/eval/results.md） | 100% 由 `scripts/run_eval.py` 生成：自动嵌入 commit hash、运行时间戳、每用例明细（含 tools/spec/backtest/numbers/refusal/judge 六列） | 人工只在报告末尾追加"结论与归因"段，**不得改动生成数据** |
| 验收报告（docs/acceptance/） | checklist 执行留痕：日期、被测版本（commit）、结果、证据引用（日志/截图/trace_id） | 不预填结果、不复填历史 |
| ADR 选型决策（docs/adr/） | 决策时间、背景、备选项、决策人（本人签名）、理由、后果——git 提交记录佐证 | 不倒填决策、不美化动机（含"为什么不用 X"的真实理由） |
| 知识库语料（evals fixtures 之外的 RAG 语料） | 每条标注来源：公开文件 URL，或"AI 生成初稿 + 人工审核"标记与审核人 | 不混入无来源内容；付费研报不内置（版权红线） |
| 指标数据（任何对外引用的数字） | 来自 /metrics 与 usage_day 表导出，或脚本生成报告 | 不手工编造对比数字 |
| 演示视频/截图 | 真实录制的线上系统操作 | 不剪辑掩盖失败画面（失败+降级路径本身是演示内容） |

## 二、角色贡献的真实口径（README/简历/面试一致）

- 本人负责：产品需求定义与 PRD 拍板、技术选型决策（每篇 ADR 决策人）、质量验收（用例设计与执行）、复盘主持、知识库语料策展与逐条审核
- 代码由 AI 编码助手按蓝图实现，本人负责需求拆解、过程监督、验收测试——**如实呈现**；对 Agent 岗位而言，"用 AI Agent 工作流交付一个 Agent 产品"本身就是工作方式的真实证明
- 不写"独立开发"，不夸大参与度；每项贡献都有对应文档/issue/提交记录可回指

## 三、工程保障真实性的机制

1. **git 全程留痕**：清晰的 commit message；每次蓝图修订一个 commit（蓝图版本记录与 commit 一一对应）
2. **GitHub Issues 为任务与缺陷唯一入口**：验收发现的问题即开 issue；postmortem 必须引用 issue 编号
3. **结构化日志落盘 + trace_id 贯穿**：任何复盘论断可回放日志原文
4. **评测报告脚本生成制**：`run_eval.py` 是 results.md 的唯一合法生产者
5. **事实参数以实测为准**：蓝图中的事实类参数（embedding 维度、hfq 稳定性、模型可用性）必须在 M0 实测后回填并注明实测日期与命令

## 四、违反本规范的处置

发现编造：删除编造内容、在对应文档记录"曾编造已纠正"（不静默处理）——这本身按真实事故复盘对待。
