## 1. P0（1 项）

### P0-1 `main.get_task` 把 jsonb 列原样返回，投研报告在前端永不渲染

- **位置**：`backend/app/main.py` `get_task`；根因关联 `backend/app/db.py`（无 jsonb codec）。
- **机理**：asyncpg 默认将 jsonb 列返回为 **str**（须显式 `set_type_codec` 才自动解码），`db.py` 未注册 codec。`tasks.result` 为 jsonb 列，`get_task` 直接 `"result": t["result"]` 返回给前端 → 前端拿到的是 JSON 字符串而非对象，`taskInfo?.result?.report` 恒为 `undefined` → `ChatBox` 的报告区永远为空。
- **影响**：核心场景 A（投研报告生成）的最终产物在页面上不可见；时间线/图表正常，故问题隐蔽。
- **为何评测没发现**：`run_eval._find_report` 恰好按 `isinstance(result, str)` 做了 `json.loads`——评测路径正确处理了字符串，掩盖了 API 路径的缺陷。`events.fetch_history`、`artifacts.summary`、`memory.recall_prefix` 也各自 `json.loads` 了，唯独 `get_task` 漏掉。
- **修复**：`get_task` 内对 `result` 做 `json.loads`（str→dict）后返回；`error`/`status` 是 text 列不受影响。不动 db.py 全局 codec（若全局注册需同步改动 fetch_history/summary/memory 等已手动 loads 的调用点，改动面大且引入回归风险；局部修复最小且可解释）。
- **验证建议**（M0/M2）：`curl /api/tasks/{id}` 断言 `result` 是对象不是字符串；前端完成一次任务后报告区非空。

## 2. P1（4 项）

### P1-1 `backup.sh` 在 cron 下必然失败

- **位置**：`deploy/backup.sh`；部署手册 cron 行 `0 4 * * * /opt/alphadesk/deploy/backup.sh`。
- **机理**：cron 执行时 cwd 为用户 HOME（非脚本目录）；`docker compose exec` 只在 cwd 查找 compose 文件（不像 git 会向上搜索）→ 第①步 pg_dump 即报 `no configuration file provided: not found`，`set -e` 退出。每日备份全部失败。第②步 `docker run -v alphadesk_appdata:...` 用显式卷名本不受 cwd 影响，但走不到。
- **修复**：脚本头部（`set -euo pipefail` 之后）加 `cd "$(dirname "$0")"`——脚本自身位于 deploy/，cd 后 compose 文件必在。已在脚本内注释说明该约束与 cron 调用方式的关系。

### P1-2 `llm.embed` 以 `threading.Lock` 跨 `await` 串行，争用时阻塞整个事件循环

- **位置**：`backend/app/llm.py` `_embed_lock` / `embed()`。
- **机理**：协程 A 进入 `with _embed_lock:`（在事件循环线程上获取 threading 锁）后 `await asyncio.to_thread(...)` 挂起让出循环；协程 B 到达 `with _embed_lock:` 时，`threading.Lock.acquire()` 是**同步阻塞调用**——在事件循环线程上原地自旋等待，A 的 embedding API 往返（秒级）期间**整个服务停摆**：心跳不续租、SSE 不推进、所有 HTTP 请求挂起。注释意图（"embed 批次串行，SDK 线程安全未承诺"）正确，原语选错。
- **触发面**：并发 `rag.search`（向量模式每查询 embed 一次）、启动探针与恢复任务运行中的检索并发等。
- **修复**：改用 `asyncio.Lock`（模块级，惰性创建避免绑定导入期事件循环的隐患可用直接创建——Python 3.10+ `asyncio.Lock()` 不再要求运行中循环，首次 await 绑定）。串行化语义不变（同一时刻仅一个协程进入临界区 → 仅一个 to_thread 工作线程调用 SDK），且等待方挂起而非阻塞循环。
- **顺带声明**（设计确认 D-4）：`chat()` 并发调用不做串行——zhipuai SDK 底层为 httpx，请求级线程安全可支撑；embed 串行是针对批量接口的保守处理。注释已补充依据。

### P1-3 embedding-2 回退路径仍传 `dimensions=1024` 参数

- **位置**：`backend/app/llm.py` `_embed_sync` / `embed()`；`backend/app/rag.py` `probe()`。
- **机理**：`dimensions` 是 embedding-3 的能力（默认 2048，可选 256/512/1024/2048，故必须显式传 1024 以匹配 DDL `vector(1024)`）；embedding-2 为**固定 1024 维**（ADR-0005 自述"固定 1024 维"），其 API 不接受 `dimensions` 参数。若服务端拒绝未知参数，回退探针 `embeddings.create(model="embedding-2", ..., dimensions=1024)` 直接异常 → probe 返回 False → **向量检索永久降级 BM25**，尽管 embedding-2 本身完全可用。
- **不确定性说明**：API 对 embedding-2 携带 dimensions 是报错还是忽略，需实测（社区行为不一）；但"fallback 模型不传 dimensions"在任何一种行为下都正确且无损——embedding-2 本就固定 1024，无需指定。
- **修复**：`_embed_sync` 增加判断——模型为 fallback（embedding-2）时不传 `dimensions`；探针的期望维度仍按 1024 校验返回值。M0-记录.md §3 新增实测项："embedding-2 不带 dimensions 调用返回 1024 维"。

### P1-4 前端事件流三处鲁棒性缺陷（合并修复）

- **位置**：`frontend/src/lib/useTaskStream.ts`、`frontend/src/lib/api.ts` `subscribe()`。
- **①历史拉取无 `closed` 守卫（竞态）**：`useEffect` 的 async IIFE 在 `await fetchEvents(...)` 返回后直接 `lastSeq.current = ...; setEvents(hist); open()`。若期间用户已提交新任务（taskId 切换→旧 effect cleanup 置 `closed=true`），旧任务的响应仍会执行 `setEvents(hist)`——**旧任务时间线覆盖新任务**，且 `lastSeq.current` 被旧任务的全局 seq 污染（task_events.id 是全局 bigserial，旧任务的 seq 完全可能高于新任务早期事件 → `append` 按 `e.seq <= lastSeq.current` 去重会**吞掉新任务的真实事件**）。`open()` 有守卫而状态更新没有，属守卫不完整。修复：`await` 之后全部置于 `if (closed) return;` 之下。
- **②async IIFE 无 try/catch**：`fetchEvents` 网络失败/非 2xx 时 Promise 拒绝在 effect 内未捕获（unhandledrejection），时间线静默卡死且无用户反馈。修复：try/catch，`setError` 提示。
- **③`subscribe` 不处理 EventSource 致命错误**：按 WHATWG 规范，EventSource 收到非 200 响应（本系统现实场景：`/api/tasks/{id}/stream` 的 **429 订阅数超上限**）会**永久失败**（fire error、不自动重连）。当前未监听 `onerror` → 时间线无提示永久停止。网络类错误浏览器会自动重连（readyState=CONNECTING），需区分。修复：`onerror` 中仅当 `readyState === EventSource.CLOSED`（致命）时给出错误提示并经退避后递归重订阅（复用 `open()`）；CONNECTING（自动重连中）不动作，避免与浏览器内置重连叠加。

## 3. P2（3 项）

### P2-1 评测器三处语义缺陷

- **位置**：`scripts/run_eval.py`、`evals/cases/backtest.yaml`。
- **①`_find_spec` 依赖被截断的事件参数**：`agent_loop` 发 `tool_call` 事件时 `args` 截断至 2000 字符；深度嵌套（≤3 层布尔）+多指标的 `strategy_spec` JSON 可逼近/超过该长度 → `json.loads(p["args"])` 失败 → `continue` → spec 恒 None → `spec_ok=False` **假阴性**（用例本身没错）。修复：解析事件失败时回退到 backtest artifact 内存储的 `strategy_spec`（`_run_backtest` 已将验证后的 `spec.model_dump()` 存入结果工件——语义上"实际执行的 spec"比"事件里的原文"更是断言对象，且经 pydantic 规范化，与 yaml 子集匹配兼容）。
- **②`tools_called` 空断言空真**：`need=[]` 时 `all(n in called for n in [])` 恒 True——报告列显示 `True` 表达"通过"，实为"未断言"。修复：`need` 为空时 `tools_ok=None`（与 `spec_ok`/`refusal_ok` 的 None 语义一致）。
- **③用例声明的 `backtest_recompute` 被忽略**：yaml 写了 `{fill: next_close, tolerance: 1e-9}`，代码硬编码比较 `next_close` 口径与 `1e-9`。声明与实现脱节（改 yaml 不生效）。修复：`run_case` 读取 `assert.backtest_recompute` 的 `fill` 与 `tolerance`（带默认值），本地复算按声明的 fill 口径执行。

### P2-2 `M_BUDGET` 计数器语义污染

- **位置**：`backend/app/metrics.py` / `orchestrator.py` `_critic_round`。
- **机理**：`M_BUDGET("budget_exceeded_total", "预算熔断")` 被以 `reason="critic_parse_failopen"` 复用——critic 输出解析失败既非预算也不是熔断，但会推高 deploy.md §5 告警口径中的 `budget_exceeded_total`（如触发"预算熔断突增"误告警）。修复：新增独立计数器 `M_CRITIC_FAILOPEN("critic_parse_failopen_total", ...)`；deploy.md §5 监控列表同步补充。

### P2-3 ChatBox 旧任务报告残留

- **位置**：`frontend/src/components/ChatBox.tsx`。
- **机理**：`taskInfo` 仅在 `done` 后 `fetchTask` 赋值，从不重置。提交新任务时 `events` 清空、时间线/图表正确切换，但**上一任务的报告 markdown 持续显示**直到新任务完成——展示层面的"张冠李戴"。修复：`useEffect(() => setTaskInfo(null), [taskId])`。

## 6. 误报/边界归档（复核为非缺陷，防后续轮次重复提出）
