## 1. P1（1 项）

### P1-1 `recover_on_boot` 预留双重释放——v16 引入、v17 未捕获

- **位置**：`backend/app/tasks.py` `recover_on_boot()`；引入轮次：v16（P1-1/P1-4 合并修复）。
- **机理**：v16 同时做了两件事——①当日 reserved 对账 upsert：`ON CONFLICT DO UPDATE SET reserved = EXCLUDED.reserved`（值为 Σ(pending.reserved)），这是**整列重置**语义，重置后的 reserved 本就不含 running 任务的预留；②循环内保留了 v15 的 `_release_of(r)`（`release_daily` 再**减去**每个 interrupted 任务的 reserved）。两者叠加 = interrupted 的预留被扣两次。
- **数字推演**：崩溃前任务 A(running, 预留 120k) + B(pending, 预留 120k)，`usage_day.reserved=240k`。重启后：upsert 置 120k（正确终态）→ 再释放 A → `GREATEST(120k-120k,0)=0`。账面 reserved=0 而 B 实占 120k。此后 `reserve_daily` 的闸门 `tokens+reserved+amount ≤ 2M` 按低估额放行——日预算可被超占（违反 PRD 非功能"击穿前 429"）。每次"崩溃时有 running 任务且存在 pending 任务"的重启都漏记一份；无 pending 任务时 GREATEST 兜底为 0 无害——所以恰在恢复逻辑的目标场景出错账。
- **为何 v17 未捕获**：需"upsert=整列替换（非累加）"与"残留的释放循环"两个 v16 变更**叠加**推演；逐行单点看各自都"合理"（upsert 注释与 _release_of 注释各自自洽）。这正是修复轮引入回归的典型形态，后续审查应在每轮修复后对"同函数内多个修复的交互"做专项过一遍。
- **修复**：删去 `recover_on_boot` 循环内 `await _release_of(r)`（事件发射与 M_TASK 计数保留）；docstring 声明机理。`watchdog_tick` 不变——它没有对账 upsert，逐个释放仍正确。`_release_of` docstring 补注"仅 watchdog 使用"。
- **边界复核**（删后正确性）：跨午夜场景（running 任务预留落昨日）——原 `_release_of` 走 `release_daily` 的 `WHERE day=current_date`，对昨日行本就无操作（D-3 已声明昨日 reserved 滞留无害），删与不删对昨日行等价；当日场景如上推演。无回归面。
- **验证建议**（M0-D2 扩展）：重启对账演练后 SQL 断言 `usage_day.reserved = Σ(tasks.reserved WHERE status='pending')`（当日行）。

## 2. P2（1 项）

### P2-1 评测 fixture 的列依赖没有约定，M0 生成快照即踩

- **位置**：`backend/app/tools.py` `_run_backtest`/`_load_fixture`、`backend/app/artifacts.py` `summary`、`evals/cases/backtest.yaml`、M0-验收清单 B3。
- **机理**：三处隐含列依赖——①`_run_backtest` 无条件求值 `open_=df["open_hfq"]`（即使默认 fill=next_close 根本不用 open 序列）；②`_price_history` 必调 `artifacts.summary`，其中访问 `close_raw/high_raw/low_raw`；③但 fixture 文件名是 `600519_hfq_...parquet`（暗示仅 hfq 列），生成方式与列契约从未钉死（`evals/fixtures/README.md` 在 FILE-MANIFEST 标"新增"但内容未入蓝图）。M0-B3 若按文件名直觉生成 hfq-only 快照，strategy agent 工具调用 KeyError 假失败，且报错落在运行期深处难以定位。
- **修复**：`_load_fixture` 加载即校验 `_FIXTURE_COLS`（hfq+raw × OHLCV 共 10 列）齐备，缺列断言报明确文案（fail-fast）；fixtures README 钉死生成契约（文件名中 hfq=信号计算口径，非列范围）；M0-验收清单 B3、评测说明 §1 同步措辞。
- **不重命名 fixture 文件**：改动面（yaml×2+清单+说明）大于收益，校验+文档已消除歧义。
